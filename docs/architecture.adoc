= randoeats Architecture
:toc: left
:toclevels: 3
:sectnums:

[.lead]
A Flutter app (iOS, Android, Web) that picks somewhere to eat, wrapped in a
60s Googie retro-future voice. Restaurant discovery runs through a Drogon
backend-for-frontend that proxies the Google Places API; everything the user
accumulates stays on their device.

== Overview

....
┌──────────────────────────────────────────────┐
│        randoeats app (Flutter)               │
│  Riverpod notifiers · Hive local storage     │
│  Dio HTTP client · google_maps_flutter       │
└───────────────────┬──────────────────────────┘
                    │  HTTPS / JSON
                    │  api.randoeats.com/api/v1/restaurants
                    ▼
        ┌───────────────────────────┐
        │   randoeats_bff (Drogon)  │  shared tekadept-bff host
        │   • holds the Places key  │
        │   • normalises responses  │
        │   • in-memory cache       │
        │   • metrics log           │
        └───────────────┬───────────┘
                        │  X-Goog-Api-Key
                        ▼
              Google Places API v1
....

The load-bearing property is that *the Google Places API key never reaches the
client*. The app talks only to the BFF; the BFF holds the key and speaks to
Google. A secondary consequence is that response shaping and caching happen
once, server-side, rather than in every platform build.

== Components

=== Flutter app (`lib/`)

Owns:: All UI, the discovery flow, filtering, ratings, and local persistence.
Ships to iOS, Android, and Web from one codebase, with `staging` and
`production` flavors (`main_staging.dart`, `main_production.dart`).
Depends on:: The randoeats BFF (restaurant data), device location via
`geolocator`, Google Maps via `google_maps_flutter`, Firebase (analytics,
Crashlytics).
Does not own:: The Google Places API key, restaurant data of record, or any
server-side user state — there is none.

=== randoeats BFF (`bff/`)

Owns:: The Google Places API key, the `/api/v1/restaurants` surface
(`RestaurantController`), request/response normalisation (`PlacesService`), an
in-memory cache (`ICache` / `InMemoryCache`), and a metrics log
(`MetricsLogger`).
Depends on:: Drogon and the Google Places API v1.
Does not own:: User identity, ratings, picks, or preferences — the BFF is
stateless with respect to users and holds no database.

Built with CMake as `randoeats_bff` and deployed via
`.github/workflows/build-push.yml` and `deploy.yml` as a container onto the
shared `tekadept-bff` host.

=== Local storage

Owns:: Everything the user accumulates — ratings (thumbs up/down), recent
picks, visited places, and settings — in Hive boxes on the device
(`lib/services/storage_service.dart`).
Does not own:: Any cross-device sync. There is no account and no login, so this
data does not survive a device change.

== Layering

randoeats does *not* use the `presentation/ -> application/ -> domain/ <- data/`
structure described in `docs/conventions.adoc`. Its actual structure under
`lib/` is:

[cols="1,3"]
|===
| Directory | Role

| `app/` | Root widget and router
| `screens/` | Screen-level UI — `splash`, `home`, `results`, `detail`, `settings`, `about`, `region_draw`
| `blocs/` | *Riverpod notifiers*, despite the name — see below
| `providers/` | Riverpod provider declarations and override wiring
| `services/` | External-service wrappers — places, location, storage, analytics, IAP, geo utils
| `models/` | Plain data models
| `widgets/` | Shared presentation, including the Googie component set
| `config/` | Theme and constants
|===

`lib/blocs/` is a *legacy directory name and contains no BLoC code*.
`flutter_bloc` is not a dependency; every file under it is Riverpod. Each
feature follows a consistent three-file shape:

* `<feature>_notifier.dart` — `class FooNotifier extends Notifier<FooState>`
  plus `final fooProvider = NotifierProvider<FooNotifier, FooState>(FooNotifier.new)`
* `<feature>_state.dart` — an `Equatable` state class, typically with a status enum
* `<feature>.dart` — a barrel export

Two features exist: `blocs/discovery/` (the reference implementation) and
`blocs/iap/`. Services are constructed in `bootstrap()` and injected via
`ProviderScope` overrides declared in `lib/providers/service_providers.dart` —
the same seam used across TekAdept Flutter projects.

The directory name is misleading enough that it has already caused documented
confusion (`AGENTS.md` exists largely to correct it). Renaming it is a refactor
and was not done here; it is recorded in `BACKLOG.adoc`.

== External dependencies and adapters

[cols="1,1,2"]
|===
| External dependency | Adapter location | Notes

| randoeats BFF (and, behind it, Google Places API v1)
| `lib/services/places_service.dart`
| Dio client. Base URL defaults to `https://api.randoeats.com/api/v1/restaurants`, overridable with `--dart-define=RANDOEATS_API_URL=...`. `Restaurant.fromBff` parses the `/nearby` response.

| Device location
| `lib/services/location_service.dart`
| `geolocator`, with permission handling.

| Hive
| `lib/services/storage_service.dart`
| All boxes opened in one place; a test-only `init(path)` path exists because `Hive.initFlutter()` needs platform channels.

| Firebase Analytics / Crashlytics
| `lib/services/analytics_service.dart`
| Provider type is `AnalyticsService?` — telemetry is optional and absent in some builds.

| Google Maps
| `google_maps_flutter` used directly in screen code
| Not wrapped behind a project-owned interface. Divergence from the ports-and-adapters rule in `docs/conventions.adoc`; recorded in `BACKLOG.adoc`.

| In-app purchase
| `lib/services/iap_service.dart` with `lib/blocs/iap/`
| Present in code. `CLAUDE.md` claimed IAP was "Not Started" — it is not.
|===

== Contracts

There is *no committed contract* for the app↔BFF boundary, which
`docs/conventions.adoc` requires. The interface is defined only by
`RestaurantController` on the server and `Restaurant.fromBff` on the client,
which can drift apart silently and fail at runtime.

This is the same gap ADR-0004 records for the sibling project shuffle_up,
arrived at independently. See `BACKLOG.adoc`.

== Data model

No server-side durable data exists. The BFF's only state is an in-memory cache
and an append-only metrics log; both are disposable.

On the device, Hive holds:

* *Ratings* — thumbs up (may surface in favourites) or thumbs down (permanently
  hidden from suggestions).
* *Recent picks* — timestamped, used to hide a place for a configurable number
  of days after it is chosen.
* *Visited places* and *user settings* — distance units, search radius, max
  results, banned categories.

Because there is no account, all of it is device-local and does not survive a
reinstall or a device change.

== Open architectural questions

* No committed schema for the app↔BFF boundary.
* `lib/blocs/` contains no BLoC code. Rename to something accurate, or accept
  the name in an ADR?
* `google_maps_flutter` is used directly rather than behind an adapter.
* The BFF has no tests and no sanitizer build, so the C++ side is outside the
  harness entirely.
* CI enforces a 60% coverage floor that has no local equivalent, so `just check`
  passing does not imply CI passing. See `MIGRATION-NOTES.adoc`.
